## What was built

- `recorder.py` — `Recorder`/`RecorderConfig`/`RecorderResult`: async poll
  loop over a `Source`'s realtime feeds, one task per feed, injectable
  `http.Clock` (real or fake) so the loop, jittered intervals, and
  `--duration` cutoff are deterministic under test with no real sleeping.
  SIGINT/SIGTERM set a stop event (handled via
  `asyncio.get_running_loop().add_signal_handler`); the loop finishes its
  current poll, flushes every spool with pending rows, and returns —
  `record start` exits non-zero only on an unhandled exception.
- `http.py` — `fetch_feed`: conditional GET (ETag/If-Modified-Since) +
  retry-with-backoff on 5xx/timeout, plus a body-hash fallback so an
  unchanged payload is skipped even against a server that ignores
  conditional headers.
- `parsing.py` — format-agnostic `vp_rows`/`tu_rows`: protobuf dispatches to
  `vp_records.py` (new, mirrors the existing `tu_records.py` style) /
  `tu_records.py` (existing, untouched); JSON dispatches to new sibling
  flatteners producing the identical column set. Malformed protobuf or
  invalid/non-object JSON raises `FeedParseError`, caught by the recorder
  and logged — never crashes the loop, never touches the spool.
- `storage/schema.py` / `storage/tu_schema.py` — added
  `staging_prefix(source_id)` (+ `curated_prefix` on the VP side), addressing
  deliverable 4: the archive prefix now comes from `Source.id` instead of
  being hardcoded to `mbta`. `BASE_PREFIX` and the old `s3_base_uri()`
  defaults are untouched literals, so `staging_prefix("mbta")` /
  `curated_prefix("mbta")` reproduce them exactly — existing archives and
  existing tests (no test referenced these constants) are unaffected.
- CLI: `record start --source <id> [--out PATH|s3://…] [--feeds vp,tu]
  [--duration S] [--dry-run] [--spool-dir] [--sources-dir] [--status-dir]`,
  `record status [--source <id>] [--json]` (spool rows/bytes, last
  `status.py` snapshot, local archive size — generic, no SIMOVI hostnames),
  `record compact` unchanged. All heavy imports stay inside command bodies
  (`--help` unaffected, still fast).
- `Dockerfile` — uv-based, non-root (`recorder` user), no secrets or agency
  values baked in; everything is `docker run` args/env. Builds from the repo
  root (needs `core`+`record`+`cli` for the `stoptimes` console script).

## Decisions worth flagging

- **`--source`/`record start` and the shared `test_cli.py`.** That file (not
  owned by T5) has `test_record_start_is_planned`, which invokes
  `record start` with **no** arguments and asserts the pre-Phase-2 "planned"
  stub contract (exit 2, "Phase 2" in output) — same for
  `test_record_help`'s `--help` listing. Per docs/PLAN.md §10 ("need a change
  elsewhere? work around it with a local shim if blocking"), I did not touch
  that file. Instead `record start`/`record status` keep `source_id` as an
  **optional** `--source` option and call the existing `planned()` helper
  when it's omitted — so a bare invocation still matches the shared test
  exactly, while `--source <id> ...` runs the real implementation. New,
  T5-owned CLI tests for the real behavior live in
  `packages/cli/tests/test_cli_record.py`. Full suite (`packages/record
  packages/cli`) passes together, including the shared file, with this
  approach — no known conflict for the orchestrator to resolve, but worth a
  second look before `test_cli.py` is eventually updated to reflect record
  being real.
- **No `record compaction` scheduling ("nightly compaction") was added.**
  The recorder's job per the task is poll → spool → flush; periodic
  compaction stays a separate, already-existing `record compact` invocation
  (e.g. cron/systemd timer in production) rather than something the poll
  loop triggers itself — nothing in CONTRACTS.md or the task description
  asked the recorder to call compaction directly, and folding it in would
  couple the loop's lifetime to compaction's (much slower, `mc`-dependent)
  one.
- **`record status`'s archive-size figure is local-archive only.** For an
  `s3://` archive it reports `archive_bytes: null` — computing S3 object
  sizes needs either `mc` (compaction's dependency, not this track's) or
  paginated `ListObjects` calls this track didn't want to add a new AWS SDK
  dependency for. Spool stats, last-poll/last-flush status, and local
  archive size are all real; this one field is a documented gap, not a
  silent omission (`record_status`'s docstring/output covers it).
- **JSON TripUpdates/VehiclePositions parsing duplicates the protobuf
  flatteners' logic** (`parsing.py`'s `_vp_rows_from_json`/`_tu_rows_from_json`
  vs. `vp_records.py`/`tu_records.py`) rather than converting protobuf to a
  dict and sharing one flattener, to keep the existing, already-tested
  protobuf path (`tu_records.py`, untouched) byte-for-byte unchanged. Tested
  for shape parity in `test_parsing.py::test_vp_rows_from_protobuf_matches_json_shape`.

## Anything unsure

- Dockerfile is untested against a real `docker build` (no Docker available
  in this environment) — reviewed by hand against the workspace's
  `uv sync --package stoptimes --extra record` wiring in `packages/cli/pyproject.toml`,
  but worth a real build before relying on it.
- `staging_prefix`/`curated_prefix` cover deliverable 4's "the prefix ...

  nothing in the task or CONTRACTS.md asked for a different partitioning
  scheme per agency, and changing it would touch `compaction/feeds.py`
  (compaction's per-feed config, not owned by this track).
