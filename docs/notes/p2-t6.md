# P2-T6 notes (val: protobuf feeds, replay, new predictors, branding)

## `pipeline:<file.py>` depends on a T4 seam that doesn't exist yet

`stoptimes.serve.pipeline` is still T4's Phase 2 placeholder module (4 lines,
no `load_pipeline`) as of this writing. `PipelineTripUpdatesPredictor`
(`packages/val/src/stoptimes/val/predictors/pipeline_adapter.py`) is built
and tested against that seam with the loader call deferred to the first
`predict()` and both failure modes (not installed / no `load_pipeline` yet)
raising a specific, actionable error — so `val` imports fine today and the
predictor will start working the moment T4 lands `load_pipeline(path) ->
Pipeline` with no change needed on this side, **provided** it matches the
shape this adapter assumes:

- `load_pipeline(path)` returns something with `.run(ctx)` per
  `core.contracts.pipeline.Pipeline`.
- The adapter builds one `PipelineContext` per `predict()` call (`source`,
  `static_feed` from `attach_static_loader`, `model=None`, `now` from the
  tick's vehicle-position epoch, and `state={"trip", "upcoming_stops",
  "vehicle_state", "trip_updates"}`) and reads results either from
  `pipeline.run(ctx)`'s return value or, if that's empty, from
  `ctx.state["predictions"]` — a convention for a pipeline whose `publish`
  stage hands off to a real sink instead of returning rows. **This
  convention is not part of the frozen `pipeline` contract** (T4/whoever
  writes `load_pipeline` should confirm or replace it) — it was the only
  reasonable way to get *something* back from a pipeline built around
  "publish hands off to a sink, returns None."
- Row shape read from either source: `stop_id` + `predicted_arrival_time`
  (a `datetime` or epoch number), dict or attribute access either way.

If T4's actual pipeline needs a different context shape (e.g. a real
`contracts.source.Source`/`StaticFeed` object rather than `trip.source` as a
bare string), this adapter needs a follow-up pass — flagging here rather than
guessing further into an unbuilt contract.

## `stoptimes:<ref>` only bridges migrated artifacts

`StoptimesArtifactPredictor` (`predictors/artifact.py`) resolves an artifact
by id or scope via `core.contracts.artifact`/`selection` correctly, but
*scoring* still delegates to `stoptimes.serve.estimator.estimate_stop_times`
using `ArtifactMetadata.legacy["model_key"]` — present only on artifacts
written by `stoptimes models migrate`. A "native" Phase 2 artifact (trained
directly into the new registry format, no `legacy` block) has no feature-
engineering bridge yet, because that's `core.features.registry`'s job (T3),
also still a placeholder module as of this writing. `predict()` raises a
clear `RuntimeError` in that case rather than guessing at features. Once
T3 ships the feature registry and a real `Model.load()`/adapter path exists
per `docs/CONTRACTS.md` §4, this predictor should switch to loading
`artifact.json` + `model.<ext>` directly and building `X` from
`artifact.features` via the registry, dropping the `estimate_stop_times`
detour entirely for non-migrated artifacts.

## Artifact registry root

`StoptimesArtifactPredictor` defaults its scan root to
`core.config.get_config().model_registry_dir` (same env vars as the legacy
`ModelRegistry`: `STOPTIMES_MODEL_REGISTRY_DIR`/`MODEL_REGISTRY_DIR`). This
is *a* reasonable default, not a contract-mandated one — `docs/CONTRACTS.md`
§7 doesn't name a canonical registry root, and the new-format
(`artifact.json` per directory) registry and the legacy flat
(`{key}.pkl`/`{key}_meta.json`) registry are different layouts that could in
principle live at different paths. If T3/the orchestrator settles on a
different canonical path for the new-format registry, update
`predictors/artifact.default_registry_dir()` (one function, easy follow-up).

## `val replay`'s `--archive`/`--archive-tu` are two flags, not one

The deliverable's example command (`--archive PATH|s3://…`) reads as a
single flag, but VehiclePositions and TripUpdates are two separate
Hive-partitioned datasets in `stoptimes.record.storage.{schema,tu_schema}`
(different `BASE_PREFIX`, different columns) — there's no single archive
root that covers both without an assumed parent-directory convention
`record` doesn't actually establish. I kept them as two flags
(`--archive` for VP, `--archive-tu` for TU, the latter optional since most
predictors besides `gtfsrt` don't need published TripUpdates at all) rather
than inventing a directory-layout convention on `record`'s behalf. This
mirrors `run --replay-vp`/`--replay-tu`, which already worked this way and
is unchanged.

## `record`'s current archive layout still bakes in "mbta"

`stoptimes.record.storage.schema.BASE_PREFIX` is literally
`"feeds/mbta/vehicle_positions"` (same for `tu_schema`) — agency-specific,
not yet generalized per `docs/PLAN.md` rule 4. Not my path to fix (T5 owns
`record/**`), but it means `val replay --archive s3://transit/feeds/<agency>/vehicle_positions`
today only really has one real `<agency>` value in this codebase. Noted for
whoever generalizes `record`'s layout.

## Branding pass scope

Renamed in user-visible strings: CLI app help/docstrings, error messages
("Run 'stoptimes val sources'..."), FastAPI app title, all Nuxt page
`<title>`s and the app-shell wordmark, `web/README.md`, `web/app/types/api.ts`
and `useApi.ts` comments, `packages/val/README.md`. **Deliberately left
alone** (data contracts, not display strings, and out of scope to change
without breaking consumers):

- `RunProvenance.etaval_git_sha`/`.etaval_dirty`/`.gtfs_eta_git_sha`/
  `.gtfs_eta_dirty` field names and their JSON keys — the web UI's
  `types/api.ts` and any persisted `*.provenance.json`/`*.summary.json`
  sidecar reads these by name.
- The `"Provenance: etaval {sha} / gtfs-eta {sha} / ..."` printed stamp —
  `packages/cli/tests/test_cli.py`-adjacent and `packages/val/tests/test_cli.py`
  (shared, not mine to edit) assert `"Provenance: etaval"` as a literal
  substring.
- `gtfs_eta:*` predictor ids themselves (kept as documented deprecated
  aliases, per the deliverable).
- `web/package.json`'s `"name": "etaval-web"` — renaming it without
  regenerating `package-lock.json` (no npm available in this pass) risks an
  `npm ci` "package.json and package-lock.json are in sync" failure; left
  as a follow-up for whoever next runs `npm install` here.

## Format-hint plumbing (`FeedFormats`) lives outside `core.domain.models.SourceConfig`

`SourceConfig` (in `core/domain/models.py`, not mine to edit) has no
`format` field, so `vehicle_positions_format`/`trip_updates_format` are read
a second time, directly off the same YAML, by
`stoptimes.val.feeds.source_config.load_feed_formats`/`load_named_feed_formats`
rather than being a `SourceConfig` field. This works today but is a bit of a
wart — if `core.domain.models.SourceConfig` is ever revisited (or replaced
by `contracts.source.Source`, which already has a proper per-feed `format`
field), this whole `FeedFormats` side-channel can be deleted in favor of
reading `Source.realtime_feeds[].format` directly.
