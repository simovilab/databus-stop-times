# P2-T7 notes (training frame)

## `build_training_frame` reuses `core.spatial.geo`, not `core.arrivals`'s own
## polyline machinery, for the spatial features

`core.arrivals` (T2) projects vehicle positions with
`core.spatial.polyline.project_point_to_polyline` + `assign_stops_monotonic`
(a Viterbi-style forward pass giving each stop a monotonic `progress_m`).
That module is built for *arrival detection* (find the crossing instant).
`build_training_frame` needs the *legacy builder's* exact feature set instead
(`distance_to_stop`, `distance_to_next_stop`, `shape_distance_to_stop`,
`shape_progress`, `cross_track_error`, `progress_ratio`) with its documented
no-shape fallback (`progress_ratio` derived from stop order + segment
progress when there's no shape at all) -- that's exactly
`core.spatial.geo.ShapePolyline` +
`calculate_distance_features_with_shape`, the function
`train.datasets.dataset_builder.build_vp_training_dataset` itself calls. So
`frame.py` builds a `ShapePolyline` from `static.trip_geometry()`'s raw
shape points and calls that function directly -- faithful to the legacy
builder's semantics, not a second geometry implementation. `core.arrivals`'s
`progress_m`-bearing `Stop`s aren't used here at all; ordering/`stops_ahead`
comes from `stop_sequence` order in the `ordered_stops` list `trip_geometry`
already returns sorted correctly.

## Target comes from a join, not local re-derivation

The legacy builder derives its own target ("first VP within N meters of the
stop") in the same pass that builds features -- duplicating exactly what
`core.arrivals.derive_arrivals` now does generally, with map-matching,
interpolation and a `reported`/`map_matched`/`interpolated` priority order.
`build_training_frame` does not re-derive anything: it looks up
`(trip_id, start_date, stop_sequence)` in the `Arrival` table the caller
already built (e.g. via `derive_arrivals`, or a hand-authored one in tests)
and takes `arrival_time` verbatim. `start_date` is resolved the same way
`core.arrivals._service_date` does (local-timezone service day fallback when
an `Observation` doesn't carry one) so a frame built from the same
observations always joins cleanly against arrivals derived from them --
kept as a small local copy (`frame._service_date`) rather than importing
`core.arrivals`'s private helper across a frozen module boundary.

**Deliberate difference from the legacy builder:** the legacy builder emits
`actual_arrival_computed` / `actual_arrival_stopped_at` / `actual_arrival`
(dual-source design, "which detector agreed"). Since the target here is a
single already-derived `Arrival` row, there is exactly one `actual_arrival`
column and one `time_to_arrival_seconds` -- no `_computed`/`_stopped_at`
variants. `core.features.registry` only ever reads `time_to_arrival_seconds`
(via `ETADataset`/`_resolve_target_column`'s fallback), so nothing downstream
needed the dual columns; the fixture (`packages/models/tests/fixtures/
sample.parquet`) has them only because it predates the `Arrival` contract.

**Also deliberate:** the legacy builder clips `time_to_arrival_seconds` to
`[0, 7200]` *inside* the builder (its STEP 5). `build_training_frame` does
not -- that clipping is `ETADataset.clean_data()`'s job downstream (which the
existing pipeline already calls: `run_experiment` -> `dataset.clean_data()`),
and folding it in here would make a row "missing its target" indistinguishable
from a row "whose target was out of range," which the track brief's
`keep_unlabeled` switch is specifically about the former. A `time_to_arrival_seconds`
< 0 (a VP sampled just after a stop's actual arrival, closest-stop matching
still returns it as `stops_ahead=0` for one row before the vehicle moves on)
is left in place, same as the legacy builder allows through its own
per-(VP, stop) loop before the final clip.

## `resolve_dataset` catalog wiring and the missing "prepared frame" `DatasetKind`

`core.catalog.models.DatasetKind` (frozen, T1's) has exactly three values:
`observations`, `arrivals`, `static`. There is no fourth "prepared training
frame" kind, even though the track brief's wording ("kind
observations/arrivals/prepared frame") implies one should exist.
`resolve_dataset`/`_load_dataset_from_catalog` therefore doesn't branch on
`kind` to decide *loadability* -- it only special-cases `kind=static` (raw
GTFS tables can never be an `ETADataset`) and otherwise just tries
`ETADataset(entry.location)`, which itself fails with a clear `KeyError`
naming the missing `vp_ts`/target column if the entry isn't actually a
prepared frame. `stoptimes data frame --register NAME` (this track's new CLI
command) registers its output under `kind=arrivals` -- the closest existing
fit (data derived downstream of the `Arrival` table) -- and tags it with
`extra={"stage": "training_frame", ...}` so a human/CLI listing can tell it
apart from a raw `Arrival` table registered by `data arrivals`. **Flagging
for the orchestrator / T1**: add a fourth `DatasetKind` value (e.g.
`training_frame` or `prepared`) in a follow-up so this doesn't have to
overload `arrivals`.

`DataSelection.sources` now resolves through the catalog by treating the
source id itself as a catalog dataset name (i.e. `sources: ["mbta"]` needs a
catalog entry literally named `"mbta"`, not "any entry whose `source_id` is
mbta") -- simplest rule that satisfies "works when the catalog has the
matching registered dataset" without guessing among multiple candidates for
one source. An unregistered source still raises `NotImplementedError`
naming exactly what's missing (kept the substring "data catalog" so the
pre-existing `test_resolve_dataset_raises_clear_error_for_sources` test,
which this track did not touch, keeps passing unmodified).

## Test-isolation gotcha found while testing catalog wiring: `core.config.get_config()` is a
## process-global singleton

`stoptimes.core.config.get_config()` caches one `ProjectConfig()` in a module
global (`_config`) for the life of the Python process, and `ProjectConfig.
__init__` reads `STOPTIMES_HOME` from the environment only once, at that
first call. A test fixture that does `monkeypatch.setenv("STOPTIMES_HOME",
...)` without also calling `stoptimes.core.config.reset_config()` only
isolates the *first* test in a given pytest process -- every later test in
the same file/session that touches `Catalog()` silently reuses the first
test's cached home directory, regardless of its own monkeypatched value.
This bit both new test files here (`test_cli_frame.py`,
`test_experiment.py`'s new catalog tests) and, on inspection, is a
pre-existing latent bug in `packages/cli/tests/test_cli_data_arrivals.py`'s
`_isolated_home` fixture (not touched here -- outside this track's owned
paths -- but its tests happen not to assert exact catalog contents across
more than one register call, so it doesn't currently surface). Worse: when
`get_config()`'s very first call in a process happens *before* any
monkeypatch fixture runs (e.g. a test with no isolation fixture at all,
like the original `test_resolve_dataset_raises_clear_error_for_sources`),
it silently caches the **real** `STOPTIMES_HOME`/cwd-relative
`./artifacts/catalog.json` for the rest of that process -- this is exactly
what happened while developing this track (stray entries leaked into the
repo's real `artifacts/catalog.json` from two separate `pytest` invocations
that shared the same cwd; deleted, not committed, not present in this
diff). Fixed locally in this track's own new/modified fixtures by calling
`reset_config()` before (and after) setting the env var. **Flagging for the
orchestrator**: `packages/cli/tests/test_cli_data_arrivals.py`'s
`_isolated_home` fixture (T1/T2's, not edited here) should get the same
`reset_config()` treatment, and it may be worth adding an autouse
session/repo-wide fixture that does this everywhere `STOPTIMES_HOME` is
monkeypatched, rather than relying on each test file remembering it.

## CLI: `stoptimes data frame`

Mirrors `data arrivals`'s shape and reuses its helpers verbatim
(`_resolve_source`, `_load_observations`, `_read_static_or_exit`); adds one
new helper, `_load_arrivals(reference)`, following the same
"catalog-name-or-path" convention as `_load_observations`. Options:
`--observations`, `--arrivals`, `--static`, `--source`, `--out`,
`--max-stops-ahead` (default 5), `--keep-unlabeled`, `--sources-dir`,
`--register`, `--overwrite`, `--json`. The JSON summary reports `rows` and
`labeled_rows` separately so a caller can see how many candidate
(position, stop) pairs had no matching arrival even when `--keep-unlabeled`
is off (those are excluded from `rows` but the counts are also logged via
`build_training_frame`'s own `logging.getLogger(__name__).info(...)` call).

## Test coverage (`packages/train/tests/test_frame.py`, `packages/cli/tests/test_cli_frame.py`)

`test_frame.py` uses a `FakeStatic` returning fixed `(shape_points, stops)`
per `trip_id`, the same straight-line-at-the-equator geometry
`packages/cli/tests/test_cli_data_arrivals.py` uses (so distances are
hand-checkable: 0.01 deg longitude ~= 1113.2 m). Covers: hand-verified
distances + target, a trip with no shape (`shape_*` columns NaN, not
fabricated), a VP past the last stop (one row, `stops_ahead=0`), a stop
missing its arrival (dropped by default, kept with NaN target under
`keep_unlabeled=True`), `max_stops_ahead` truncation, determinism (shuffled
input row order produces an identical, sorted output frame), an unknown
`trip_id` (contributes zero rows, empty-frame column shape verified), and a
superset check against the non-temporal features `examples/experiments/
xgb-baseline.yaml` names. `test_cli_frame.py` reuses the same static/VP
fixture builders as `test_cli_data_arrivals.py` and additionally verifies:
catalog registration (`--register`), `--max-stops-ahead`, a clear error for
a missing static feed, and resolving `--arrivals` from a catalog-registered
name (not just a path).

## Not done / open

- `resolve_dataset` supports exactly one `sources` or one `datasets` entry,
  matching the existing (pre-T7) one-dataset-name limitation noted in
  `docs/notes/p2-t3.md`; multi-source stitching (e.g. training across
  `sources: [mbta, bucr]`) is not implemented.
- `sources` resolution requires a catalog entry named exactly the source id;
  it does not search by `DatasetEntry.source_id` among differently-named
  entries. Simplest unambiguous rule for now -- revisit once there's a real
  multi-dataset-per-source use case.
