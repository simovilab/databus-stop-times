# U3 · Diagnose — notes for the orchestrator

## What was built

- `packages/core/src/stoptimes/core/diagnose/` (package, not a single file —
  it was going to exceed ~400 lines in one module):
  - `models.py` — `Severity`, `Finding`, `DiagnoseParams`, `DiagnosticReport`
    (pydantic, `extra="forbid"`, same style as `contracts.data`). The report
    is data: rendering lives entirely in the CLI.
  - `_util.py` — `bounded_samples` (caps a finding's sample list at
    `max_samples`) and `severity_by_share` (blocker once an affected share
    crosses `majority_threshold`).
  - `vp_checks.py` / `tu_checks.py` — realtime-only checks (presence,
    gaps/distribution, duplicates, out-of-order, staleness, missing
    lat/lon or arrival/departure times). All vectorized pandas
    (`groupby`/`diff`/boolean masks), no per-row loops, per the "sensible
    on a large archive" requirement.
  - `static_checks.py` — checks needing the GTFS static feed: required
    tables present, shapes.txt present, `shape_dist_traveled` coverage,
    trip_id/route_id/stop_id overlap between static and observed.
  - `__init__.py` — `diagnose_feed(...)`, the pure orchestration function
    (no I/O), plus worst-severity-wins verdict aggregation.
- `packages/core/tests/test_diagnose.py` — 18 tests, including the
  "only trip updates, no shapes, no vehicle positions" newcomer-broken-case
  scenario, a full clean-feed run, and every individual check.
- `packages/cli/src/stoptimes/cli/commands/diagnose.py` — replaced the
  `planned(...)` placeholder. Options: `--static`, `--vehicle-positions`
  (+ `--vehicle-positions-format`), `--trip-updates` (+
  `--trip-updates-format`), `--source`, `--sources-dir`, the four
  `DiagnoseParams` thresholds as CLI flags, `--json`. `--source` alone (no
  explicit locations) resolves an agency YAML the same way `data.py` does
  and reads its configured feeds via `readers.read_observations_for_source`.
  Exit code is 0 whenever the report was produced, non-zero only if a given
  location couldn't actually be read (bad path/URL/format).

## Design decisions worth flagging

- **Severity is three-valued, not scored**: `blocker` / `degraded` / `info`.
  A numeric score would imply precision the underlying counts don't
  support. `severity_by_share`'s `majority_threshold` (default 0.5) is the
  one place a share crossing a line changes severity, and it's a named,
  documented `DiagnoseParams` field, not a buried constant.
- **`shape_dist_traveled` wording is grounded in the actual fallback
  behavior**, not a guess: `stoptimes.core.spatial.polyline.build_polyline`
  falls back to cumulative haversine distance between shape points when any
  point in a shape lacks `shape_dist_traveled` (see that module's
  docstring/comments). The finding's `blocks` text says exactly that. I did
  **not** add a check for `stop_times.shape_dist_traveled` — nothing in
  `core.arrivals`/`core.spatial` currently reads it, so a finding about it
  would be dishonest about what it blocks.
- **Trip-updates absence is `degraded`, not `blocker`**: VP + static is
  still sufficient to train from; TU is needed to validate/serve, not to
  train. Static absence and VP absence are both `blocker` (the former
  because `core.arrivals.derive_arrivals` requires a static feed
  unconditionally; the latter because it's the only source of positions to
  map-match).
- **Staleness uses `ingested_at - ts`**, not wall-clock-now, so it works
  identically on a historical archive and a live poll — `ingested_at` is
  set by the reader at fetch time either way (`readers.py`'s
  `_finalize_vp_frame`/`_finalize_tu_frame`, and carried through the
  archive by `record`). When `ingested_at` is entirely absent (e.g. an AVL
  CSV import), staleness degrades to an `info` finding explaining why it
  couldn't be checked, rather than silently skipping.
- **`diagnose` reused by `data inspect`**: PLAN.md's U3 row says "reused by
  `data inspect`" but wiring that reuse means editing
  `packages/cli/src/stoptimes/cli/commands/data.py`, which is out of scope
  (owned by the U2 CLI-polish track, worked in parallel). `diagnose_feed`
  is a plain function over already-read frames + optional static loader, so
  whoever owns `data.py` can call it directly (`from stoptimes.core.diagnose
  import diagnose_feed`) without needing anything from me. Flagging here so
  the orchestrator knows the reuse isn't wired yet.

## Dependency needs

None. `diagnose` uses only what `stoptimes.core.readers`/`gtfs.static`/
`contracts` already depend on (pandas, pydantic); no new extra needed.

## Anything I was unsure about

- The CLI's `--vehicle-positions`/`--trip-updates` two-option shape departs
  from the plan's literal `--observations` example, because `diagnose`
  genuinely needs both VP and TU frames (they're different schemas/kinds
  and `readers` reads them separately), unlike `data add`/`data inspect`
  which operate on one dataset at a time. Also added `--*-format` overrides
  and reused `data add`'s catalog-dataset-name-or-path/URL resolution
  convention so a name registered with `data add` works directly as either
  option's value.
- Kept `stop_times.shape_dist_traveled` out of the shapes finding (see
  above) even though the GTFS spec recommends it — happy to add it back if
  a later track wires it into map-matching and the claim becomes true.
