# T1 · Data — notes for the orchestrator

## Dependency needs (not added to any `pyproject.toml` — T1 doesn't own those)

- **`fsspec` (+ a protocol package, e.g. `s3fs`) for `s3://` archive reads.**
  `stoptimes-core` has no extra for this today. `readers.read_archive_parquet`
  imports `fsspec` lazily and raises a clear `ImportError` if it's missing;
  local-path archives need nothing extra. Recommend a new `stoptimes-core[s3]`
  extra (`fsspec>=2024.6`, `s3fs`) mirroring the existing `[pb]`/`[parquet]`
  pattern — `stoptimes-val` already declares almost this exact extra
  (`extra == 's3'` in `uv.lock`), so it may be reusable rather than
  duplicated. Untested here: no s3 credentials/network in this sandbox, and
  `fsspec` isn't installed in the dev venv, so `read_archive_parquet`'s
  `s3://` branch is implemented but not exercised by a test.
- `gtfs-realtime-bindings` and `pyarrow` are already declared as `stoptimes-core`
  extras (`[pb]`, `[parquet]`) and are present in the dev group transitively
  (via `stoptimes[all]` → record/val), so protobuf and parquet tests run for
  real rather than being skipped.

## Known limitations / follow-ups

1. **`bearing` and several TU fields are not reachable through
   `core.realtime.gtfsrt_json`'s existing parse functions.**
   `parse_vp_feed`'s `VehicleState` has no `bearing` field, and
   `parse_tu_feed`'s `TripUpdateRecord`/`StopTimeUpdate` carry neither
   delay/uncertainty/schedule_relationship nor `revenue` — all of which
   `contracts.data.Observation`/`OBSERVATION_TU_SCHEMA` need. Rather than
   widen those dataclasses (out of scope — `core/realtime/gtfsrt_json.py`
   isn't an owned T1 path) `readers.py` parses the feed dict directly,
   reusing `gtfsrt_json`'s private `_opt_float`/`_opt_int`/`_opt_str`
   accessor helpers for the defensive-access style. Recommend a future pass
   extend `VehiclePositionRecord`/`TripUpdateRecord` to carry these fields so
   other consumers of `parse_vp_feed`/`parse_tu_feed` don't have to
   re-parse.
2. **`revenue`'s wire format is genuinely unclear.** It isn't a standard
   GTFS-RT field in the versions this repo targets; `readers.py` reads
   `trip_update.revenue` defensively (best-effort, usually absent →
   column omitted, since `OBSERVATION_TU_SCHEMA` marks it optional and
   fabricating a value would be worse than omitting the column). Confirm the
   real field path against whichever agency actually emits it before relying
   on this in T2/T3.
3. **AVL CSV rows with no `trip` column in the mapping get `trip_id=""`.**
   Trip inference from a bare AVL trace (bUCR's case) is T2's job
   (`docs/PLAN.md` T2 owns `core/arrivals.py` + bUCR-specific inference under
   `train/sources/**`); T1's `ColumnMapping`/`read_avl_csv` only gets the
   trace into the `Observation` shape, unassigned to any trip.
4. **`OBSERVATION_TU_SCHEMA` (contracts/data.py) has no `schedule_relationship`
   column**, even though `Observation.schedule_relationship` is a real field
   and `docs/CONTRACTS.md`'s open question 3 recommends readers expose a
   normalized enum column "next to it". `read_gtfsrt_json`/`_protobuf` add
   both `schedule_relationship` (raw) and `schedule_relationship_norm` /
   `trip_schedule_relationship_norm` (via `contracts.prediction`'s existing
   `StopScheduleRelationship`/`TripScheduleRelationship` enums) as columns
   beyond the schema — `validate_frame` ignores extra columns, so this
   doesn't break validation, but a future contracts pass might want to add
   `schedule_relationship` to `OBSERVATION_TU_SCHEMA` properly.
5. **`data inspect`'s "trips matched static"** needs `--static PATH` passed
   explicitly (no dataset-to-static linkage in the catalog yet); T3/U3's
   `diagnose` report (docs/PLAN.md §7 U3) may want to promote that into a
   catalog-level relationship instead of a per-invocation flag.

## Expected shared-file test breakage (docs/PLAN.md §10: "own only your paths")

`packages/cli/tests/test_cli.py` (not owned by T1) has
`test_data_add_is_planned` and `test_data_inspect_is_planned`, asserting the
*old* `planned()` stub behavior (exit code 2, "Phase 2" in the output) for
`data add`/`data inspect`. Implementing those commands for real (this
track's explicit deliverable) makes both fail — `data add`/`data inspect`
now exit 0 (or 1 on a real usage error) and never print "Phase 2". This is
expected, not a regression to chase: `test_data_arrivals_is_planned` still
passes (arrivals stays a stub, T2's job), and the new, owned
`packages/cli/tests/test_cli_data.py` covers `data add`/`list`/`inspect`/
`remove` for real. The orchestrator should update or remove the two stale
assertions in `test_cli.py` when merging this track.
