  (12 tests), `packages/train/tests/test_api.py` (4 tests, including a full

  both build a synthetic one-route/four-stop/four-trip feed inline (same

## CLI-command-to-API-function rewiring map

The orchestrator should point each CLI command's body at these functions
(no CLI files were edited by this track — they're off limits). In every
case the CLI command becomes argument parsing + one call + printing/`--json`.

| CLI command | API function |
|---|---|
| `data add` | `stoptimes.core.api.add_dataset` |
| `data list` | `stoptimes.core.api.list_datasets` |
| `data inspect` | `stoptimes.core.api.inspect_dataset` |
| `data remove` | `stoptimes.core.api.remove_dataset` |
| `data arrivals` | `stoptimes.core.api.build_arrivals_dataset` |
| `data frame` | `stoptimes.train.api.build_frame` |
| `diagnose` | `stoptimes.core.api.diagnose` |
| `train run` (non-dry-run) | `stoptimes.train.api.run_experiment_from_file` |
| `train run --dry-run` | `stoptimes.train.api.plan_experiment` + `.load_experiment` |
| `models list` | `stoptimes.core.api.list_models` |
| `models card` | `stoptimes.core.api.model_card` |
| `models promote` | `stoptimes.core.api.promote_model` |
| `serve` (the `--model`-resolution half) | `stoptimes.train.api.select_model` |
| `serve` (the pipeline-run half) | `stoptimes.train.api.predict_once` — see caveat below |
| `val replay` | `stoptimes.val.api_verbs.replay_score` |
| `val report` (metrics section only — the sensitivity table stays CLI-only, it needs the run's live SQLite `--db`, not just the exported rows) | `stoptimes.val.api_verbs.score_report` |

`data add`/`data inspect`/`diagnose` keep their exact auto-format-guessing
and catalog-entry-shape logic — it moved into `core.api`/`_catalog.py`
verbatim; the CLI functions in `cli/commands/data.py` and
`cli/commands/diagnose.py` currently duplicate all of it inline. Rewiring
those two files is a straightforward "call the function, drop the inlined
body" edit, not a behavior change.

`data arrivals`/`data frame` are the same story: `build_arrivals_dataset`/
`build_frame` are a byte-for-byte port of `data_arrivals`/`data_frame`'s
bodies, including the `--register`/`--overwrite` handling and the exact
summary-dict shape the `--json` flag prints today.

## Not covered (intentionally out of scope for this track)

- `models migrate` and `models check`: both need `stoptimes.models`
  directly (`stoptimes.models.compat.migrate`, `stoptimes.models.check_registry`),
  which is `packages/models/**` — off limits (another agent is actively
  rewriting it in parallel). No API wrapper was added; the CLI can keep
  calling `stoptimes.models.compat.migrate.migrate` directly, or the
  orchestrator can add a thin `packages/models/src/stoptimes/models/api.py`
  itself once that track lands.
- `record start/compact/status`: no Python API verb was added for these.
  They weren't named in the task's end-to-end chain (read → arrivals →
  frame → train → select/predict → replay-score), and `packages/record/**`
  is a different track's territory; adding one would mean guessing at
  ownership. Flagging for the orchestrator to decide whether a U4-shaped
  `stoptimes.record.api` belongs to this track or record's own.
- `train ui` (the Textual TUI) has no non-interactive API equivalent by
  nature — nothing to wrap.
- `val run`/`val sources`/`val figures`: `sources` is a trivial listing
  (`stoptimes.val.feeds.source_config.list_sources`, already a plain
  function — no wrapper needed); `run` is the live-feed loop (out of scope
  for a notebook, which wants determinism); `figures` renders PNGs via
  matplotlib, not data, so it doesn't fit "returns are data, not printed
  output" and was left as a CLI-only convenience.

## `import stoptimes` vs. `stoptimes.core.api`

Per docs/PLAN.md §2, `stoptimes` is an implicit PEP 420 namespace package —
**there is no `stoptimes/__init__.py` anywhere in the workspace**, and this
track doesn't own a path where one could be added even if it wanted to
(the owned paths are `packages/core/src/stoptimes/core/api.py` and similar
subpaths, not `packages/core/src/stoptimes/__init__.py`). That means
`import stoptimes; stoptimes.add_dataset(...)` **does not work today** and
can't be made to work without an orchestrator-level decision (a root
`stoptimes/__init__.py` in one member package would need to combine cleanly
with the six others' namespace contributions, and would need a home —
probably `packages/cli`, since it's the only member that already depends on
everything else — that isn't this track's call to make).

The functions are "importable as `stoptimes`" in the sense that every
import path starts with `stoptimes`:

```python
from stoptimes.core.api import add_dataset, build_arrivals_dataset, diagnose, resolve_source
from stoptimes.train.api import build_frame, run_experiment_from_file, select_model, predict_once
from stoptimes.val.api_verbs import replay_score, score_report
```

If the orchestrator wants a literal `import stoptimes; stoptimes.<verb>()`
surface, the cheapest option is a small `packages/cli/src/stoptimes/__init__.py`
(the CLI package already depends on core/train/val, so it's the one place
that dependency direction doesn't conflict with rule 1) that lazily
re-exports the three modules' `__all__`. Left to the orchestrator: adding a
`stoptimes/__init__.py` is a whole-workspace decision, not a U4-owned one.

## Dependency direction (docs/PLAN.md §1 rule 1)

Verified by import-time inspection (`import stoptimes.core.api` then
checking `sys.modules` for any `stoptimes.train`/`stoptimes.val`/
`stoptimes.serve` entry — none leak): `core.api` never imports `train`/
`serve`/`val`, even transitively. `train.api` imports `stoptimes.serve`
lazily, inside `select_model`/`predict_once` only, so `import
stoptimes.train.api` alone doesn't pull in serve's dependency stack either.

## Optional dependencies stay optional

`stoptimes.core.api` only needs what `stoptimes-core` already declares
(pandas/pydantic/yaml/httpx) — no new optional-dependency surface. Reading
protobuf/parquet/s3 archives still raises the same `ImportError` with the
same install hint as `stoptimes.core.readers` always has; `core.api` doesn't
catch or reword those. `train.api.select_model`/`predict_once` need
`stoptimes-serve` installed (`stoptimes-train` already depends on it per
docs/PLAN.md's dependency graph, so this is not a *new* optional edge, just
a lazily-imported one within an already-required dependency).

## Async in a notebook: `stoptimes.val.api_verbs.replay_score`

`stoptimes.val.engine.runtime.run_engine` is a coroutine; the CLI calls it
with a bare `asyncio.run(...)`, which is fine from a script but raises
`RuntimeError: asyncio.run() cannot be called from a running event loop`
inside a Jupyter/IPython kernel (which already runs one). `replay_score`
works around this with `_run_in_thread_if_loop_running`: if no loop is
running it calls straight through; if one is (notebook), it runs the whole
`SqliteStorage(":memory:") + asyncio.run(run_engine(...)) + load_results()`
sequence on a worker thread instead — the in-memory SQLite connection has to
be created and used on that same thread (`sqlite3` objects aren't
cross-thread-safe), which is why the connection isn't created before the
thread hand-off. This was caught by actually executing
`01_end_to_end.ipynb` (see below), not by reasoning about it — worth every
non-CLI async-calling verb watching for the same class of bug as more of
the API gets built out.

## `stoptimes.train.api.predict_once` and U6

`predict_once` mirrors `cli/commands/serve.py`'s `--once` body (model
resolution + pipeline construction + one `pipeline.run(ctx)` + summary
dict) as it exists today, in Phase 3 before U6 rebuilds `serve.estimator`
onto `serve.pipeline`. It was placed in `stoptimes.train.api` rather than
`stoptimes.serve` because `packages/serve/**` is off limits (U6 is actively
rewriting it in parallel) — this track owns no path there to add a
`serve.api` module to. Once U6 lands, the orchestrator should sanity-check
that `predict_once`'s three imports (`serve.model_loading`,
`serve.pipeline.build_default_pipeline`/`load_pipeline`, `serve.sinks
.sink_from_uri`) still have the same signatures, and consider whether this
function's real home is a `stoptimes.serve.api` module instead, with
`stoptimes.train.api.predict_once` becoming a re-export for backward
compatibility.

## How the notebooks were verified

`nbformat`/`nbclient`/`ipykernel` aren't (and shouldn't become) project
dependencies — adding them would mean editing `pyproject.toml`/`uv.lock`,
both off limits for every track. They were used only as an ephemeral
overlay via `uv run --with nbclient --with ipykernel jupyter execute
--inplace examples/notebooks/*.ipynb` (`uv run --with` layers packages on
top of the existing synced environment for one invocation without touching
the lockfile), which executed both notebooks against the real project
environment top to bottom with no errors, then `uv run --with jupyter
jupyter nbconvert --clear-output --inplace ...` cleared the outputs
afterward. Reproducible by the orchestrator with the same two commands; no
new tooling was installed into the repo.
