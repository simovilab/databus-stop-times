# F1 — val predictor adapters (defects from the newcomer usertest)

Scope: `pipeline:<file.py>` adapter, predictor-error surfacing, and the
legacy `MODEL_REGISTRY_DIR` warning. See the tester's report at
`/tmp/stoptimes-usertest` and `/tmp/stoptimes-wheeltest` (not modified).

## 1. `pipeline:` adapter fix

`pipeline_adapter.py`'s `_ensure_pipeline` passed a bare `Path` into
`load_pipeline`, which requires a `"spec:attr"` string. Fixed by building the
spec in a new `_spec()` helper:

- If the raw predictor path already contains a `:` (e.g.
  `pipeline:my_pipeline.py:my_attr`), pass it straight through unchanged —
  a user who wants a non-default attribute name can still ask for it.
- Otherwise (the documented bare form, `pipeline:my_pipeline.py`), default
  the attribute to `"pipeline"` — every example in the docs/tester's own
  `val_pipeline.py` names its pipeline object `pipeline = build_default_pipeline()`.
- Wrapped the `load_pipeline()` call so an `AttributeError` on the defaulted
  case raises a message naming the file and the default attribute it looked
  for, and how to override it explicitly, instead of a bare
  `module has no attribute 'pipeline'`.

This was verified against the tester's real fixtures (see "End-to-end
verification" below), not just the unit tests.

## 2. Predictor error surfacing

Added to `RunSummary` (`engine/runtime.py`): `predictor_first_error: dict[str, str]`
(first exception's `"Type: message"` per predictor_id, set once via
`.setdefault`) and `predictor_attempts: dict[str, int]` (total predict()
calls per predictor_id, success + failure). Both round-trip through
`to_dict()`/`from_dict()`, so `summary.json` keeps the cause on a
non-interactive run.

`run_engine`'s per-predictor try/except now increments `predictor_attempts`
before the call and records the first exception the first time a given
predictor_id fails.

CLI (`_report_run` in `cli/main.py`): for each predictor with errors, prints
one line naming the exception type + message (not a traceback, and not all
103 of them — just the first one, which is what actually happened).
**Judgement call**: when `predictor_errors[pid] == predictor_attempts[pid]`
(every single attempt failed), the line is escalated to
`FAILED EVERY TICK: ... -- first cause: ...` and routed to stderr — a
predictor that never produced a single prediction is a run failure, not a
footnote, even though the run's exit code stays 0 (other predictors/the run
itself may have succeeded; a partial predictor failure alone doesn't seem
worth hard-failing the whole `val replay` invocation, but it must not read
as quiet). A predictor that only fails sometimes gets the quieter one-line
form on stdout. This is a judgement call, not dictated by the ticket — happy
to revisit if the orchestrator wants full-failure to also set a non-zero
exit code.

## 3. Legacy `MODEL_REGISTRY_DIR` warning

`gtfs_eta_models.py` ran its `MODEL_REGISTRY_DIR` auto-resolve-or-warn logic
at **module import time**, unconditionally. `engine/assembly.py` imports
this module eagerly (to register the `gtfs_eta:*`/`stoptimes:*` predictor
factories) on every `stoptimes val` invocation, so every newcomer saw the
warning regardless of which predictor they actually used.

Fixed by moving that logic into `_ensure_model_registry_env()`, called once
(memoized on a module-level flag) from `GtfsEtaModelPredictor.__init__`
instead of at import time. A newcomer who never constructs a
`GtfsEtaModelPredictor` (i.e. never uses `gtfs_eta:*`/`stoptimes:*`) never
sees it. Anyone actually on that path still gets the exact same warning the
first time they construct one — verified `test_gtfs_eta_predictor.py` still
triggers it (see full-suite warnings summary), and the new
`test_pipeline_adapter_cli.py::test_pipeline_predictor_run_does_not_emit_legacy_model_registry_warning`
asserts a `pipeline:`-only run does not.

This module and `packages/models/src/stoptimes/models/common/registry.py`
were both in scope per the task; the fix only needed `gtfs_eta_models.py`
(this package). Skimmed `registry.py` — it doesn't reference
`MODEL_REGISTRY_DIR` or emit this warning, so no note filed against
`packages/models`.
