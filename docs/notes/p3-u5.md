## Dependency needs (I did not touch `pyproject.toml`/`uv.lock`)

Add a docs dependency group, e.g. in root `pyproject.toml`:

```toml
[dependency-groups]
docs = ["mkdocs-material>=9.5"]
```

`mkdocs-material` alone is sufficient — I deliberately did **not** reach for
`mkdocs-click`/`mkdocs-gen-files` for the CLI reference; see below for why.

## CLI reference: generated, not hand-copied, but not live-generated at `mkdocs build` time

`docs/scripts/gen_cli_reference.py` imports `stoptimes.cli.main.app`, walks its command tree
with Click's own `get_help()` formatter (via `typer.main.get_command(app)`), and writes
`docs/reference/cli.md`. Run it after any CLI change:

```bash
uv run --no-sync python docs/scripts/gen_cli_reference.py
```

This is real generation (every line is Click's own formatter output, so it cannot drift the
way hand-copied `--help` text would), but it's a script you re-run and commit, not a
mkdocs-build-time plugin (`mkdocs-gen-files` + `mkdocs-click`) — that would need two more
dependencies I'm not authorized to add, for a payoff (regenerating on every `mkdocs serve`
reload) that doesn't matter for a reference page that changes only when the CLI does.
**Recommendation for the orchestrator**: fine to leave as a script; if the docs group ever
wants build-time generation, add `mkdocs-gen-files` and `mkdocs-click` and I'll wire it.

One non-obvious thing this script had to work around: Typer vendors its own click fork
(`typer.core.TyperGroup` is not an `isinstance` of the real `click.Group` installed
alongside it), so the recursive walk duck-types on `hasattr(cmd, "commands")` instead of
`isinstance(cmd, click.Group)` — the natural-looking code silently visited only the root
command otherwise.

## Filesystem gotcha found while writing this: `docs/CONTRACTS.md` and a same-directory
## `docs/contracts.md` are the same file here

This checkout sits on a case-insensitive filesystem (macOS/APFS default). `docs/CONTRACTS.md`
and a hypothetical `docs/contracts.md` resolve to the same inode — writing one **is** writing
the other. I originally planned a `docs/contracts.md` orientation page (as the brief's own
wording, "Contracts — surface CONTRACTS.md," suggests); the `Write` tool refused it because
it collided with the already-read `CONTRACTS.md`. Renamed my page to
`docs/contracts-overview.md` instead and fixed every internal link. **Flagging for anyone
else on a case-sensitive CI runner or Linux dev box**: this isn't a problem there (two
distinct files), but don't introduce a real `docs/contracts.md` later without checking this
note, or it will silently clobber `docs/CONTRACTS.md` for every macOS contributor.

## Bugs / rough edges found while following my own instructions (not fixed — outside owned paths)

1. **`stoptimes record start`/`status` default `--status-dir` to a hard-coded
   `/var/lib/simovi/status`** (`stoptimes.record.status.DEFAULT_STATUS_DIR`, in
   `packages/record/src/stoptimes/record/status.py`). This is SIMOVI-specific and violates
   `docs/PLAN.md` rule 4 ("no agency-specific code in `packages/`"); it also fails outright
   with a `PermissionError`/`FileNotFoundError` traceback (not a clean CLI error) on any
   machine that isn't that VPS. I worked around it in every guide by always passing
   `--status-dir` explicitly, and called it out with a warning admonition in
   `guides/record-a-feed.md`. Owned by whoever owns `packages/record` — not this track.

2. **`stoptimes record compact` is still the legacy compaction CLI verbatim**
   (argparse-based, `--alias`/`--bucket` defaulting to `simovilab`/`transit`, `--feed
   {mbta_vp,bucr_navsat}`) — visibly agency-specific, not a `--source`-driven generic
   command like the rest of `stoptimes record`. Documented as a known pass-through in
   `guides/record-a-feed.md` rather than describing behavior it doesn't have.

3. **Every `stoptimes val <subcommand>` (including `--help` on a leaf subcommand like
   `val replay --help`) takes 20-60 seconds on first invocation** in a fresh process,
   because the forwarding-stub commands `docs/notes/p3-u2.md` added still pay the full
   `sklearn`+`matplotlib` import chain the moment the real subcommand runs (only the
   *group*-level `stoptimes val --help` stayed fast). The first time I hit this it looked
   exactly like a hang — I let one run to completion unmodified (`val version`, ~30s) to
   confirm it always finishes rather than being stuck. Documented as a real, expected delay
   (not a hang) with a note admonition in `guides/validate-a-feed.md` and the quickstart,
   since a stranger hitting this with no warning would reasonably assume something's broken
   and Ctrl-C out. Worth a real fix (lazy-import the predictor registry and
   `matplotlib.pyplot`, as `docs/notes/p3-u2.md` itself already recommends as a follow-up)
   before the Phase 3 gate — 20-60s of silence on the very first command a stranger runs
   after `--help` is a bad first impression even though it's not a bug in the "wrong answer"
   sense.

4. `readers.read_archive_parquet` has no column-projection parameter (noted already in
   `docs/notes/p3-u3.md`; confirmed again here while writing the diagnose guide) — a
   `--from`/`--to`-bounded read still loads every column of every matched file.
