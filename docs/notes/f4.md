# F4 — feature contract: refuse an unproducible required feature

## Defect (docs/PLAN.md §7.4)

`serve.pipeline.default_features` was a pre-registry stopgap: it computed
temporal features directly (not through `core.features.registry`, even
though T3 landed in Phase 2) and merged whatever `match` attached to
`.extra`. `default_predict` then built each model input row with
`{name: row.get(name) for name in required}` -- a feature the pipeline
couldn't produce silently arrived as `None`. Nothing compared an artifact's
`required_features` against what serving can actually compute, so a model
trained on VP geometry, segment identity, or rolling-conditions features was
either served on missing inputs (families that impute, e.g.
`HistoricalMeanModel` -- confident nonsense) or failed per row into the
errors list. Never refused.

## Fix

**1. Registry wired into `default_features`** (`packages/serve/src/stoptimes/serve/pipeline.py`).
Temporal columns (`hour`, `day_of_week`, `is_weekend`, `is_holiday`,
`time_of_day_bin`, `is_peak_hour`, `hour_sin`/`hour_cos`/`dow_sin`/`dow_cos`)
now go through `core.features.registry.build()` against a `_ts` timestamp
column, instead of calling `core.features.temporal.extract_temporal_features`
directly -- same values, same tz/holiday-region defaults, but through the
one place training and serving are both supposed to agree on what "temporal"
means. Spatial features still come from whatever `default_match` attached to
`.extra` (unchanged) -- `core` is not allowed to call `train`-owned dataset
builders (see the registry module's own docstring), so `core.features.registry`
only *describes* those columns; nothing in `core` or `serve` can compute
`shape_progress`/`vp_lat`/`recent_seg_traversal_s`/etc. live from a single
realtime observation.

Two new pure functions name the split explicitly:
- `producible_features()` -- every registry "temporal" feature, the three
  spatial columns `default_match` actually attaches
  (`distance_to_stop`/`stops_ahead`/`cross_track_error`), and the
  trip/stop identity columns always present on a `MatchedObservation`.
- `unproducible_registered_features(required)` -- which of `required` the
  registry knows about but isn't in `producible_features()`. A name the
  registry has never heard of (BYO/legacy feature columns, e.g. this
  package's own tests' `features=["x"]`) is left alone -- no positive
  evidence it's unproducible, same principle `check_version_drift` already
  uses for an artifact with no recorded library versions.

**2. Refusal at model-load time**
(`packages/serve/src/stoptimes/serve/model_loading.py`,
`check_feature_producibility` + `UnproducibleFeaturesError`, called from
`load_artifact_model` right after `check_version_drift`). Modeled directly
on U7's `ArtifactVersionDriftError`: names the missing feature(s), says what
would have to produce them (a `stoptimes.train.datasets` builder, not this
pipeline), and how to proceed (retrain on producible features, or override).

**Why `UnproducibleFeaturesError` subclasses `ArtifactVersionDriftError`
instead of `RuntimeError`:** `packages/cli/src/stoptimes/cli/commands/serve.py`
(not owned by this track) catches exactly
`except (NotImplementedError, ArtifactVersionDriftError)` around
`load_artifact_model` and prints the message instead of a traceback. I could
not edit that file, so I derived the new error from a type it already
catches rather than filing a note and leaving the refusal to surface as an
uncaught traceback in the interim. **Orchestrator note:** the semantics are
conflated (this isn't a version-drift condition) -- next time `serve.py` is
touched, consider widening its except clause to a shared
`ArtifactRefusalError` base and un-subclassing `UnproducibleFeaturesError`
from `ArtifactVersionDriftError`. Low urgency: the current inheritance is
behaviorally correct and documented at the class definition.

**Override**: `STOPTIMES_ALLOW_UNPRODUCIBLE_FEATURES` (same grammar as
`STOPTIMES_ALLOW_VERSION_DRIFT`; deliberately a separate env var so
overriding one refusal doesn't silently override the other) or
`allow_unproducible_features=True` on `load_artifact_model`. Warranted
because this check runs at model-load time, *before* the CLI has picked a
pipeline (`serve.py` loads the model, then decides `--pipeline` vs.
`build_default_pipeline()`) -- a custom `--pipeline` whose own `features`
stage legitimately supplies the "unproducible" column another way has no
way to signal that to this check, so an explicit, loudly-logged override is
the only escape hatch available without restructuring `serve.py`'s call
order (out of scope, not owned by this track).

**3. `val`'s seam preserved.** `StoptimesArtifactPredictor` (F2,
`packages/val/src/stoptimes/val/predictors/artifact.py`) calls
`serve.model_loading.load_artifact_model` and
`serve.pipeline.default_features`/`default_predict` directly -- both changed
functions' signatures are backward compatible (new params default to `None`/
env-var-controlled), so no `val` edit was needed. Not touched.
`packages/val/tests/test_artifact_predictor_native.py` still passes (2/2).

  fixture, both via `uv run stoptimes`, not mocked):
  - `f4-producible` (features `[distance_to_stop, stops_ahead, hour]`):
    `{"source": "demo", "artifact_id": "f4-producible", ...,
    "trip_update_count": 4, "errors": [], "published": true}` -- served
    normally.
  - `f4-unproducible` (features `[distance_to_stop, shape_progress, hour]`):
    `✗ artifact 'f4-unproducible' requires feature(s) ['shape_progress']
    that stoptimes serve's default pipeline cannot compute: ... retrain ...
    or ... override with STOPTIMES_ALLOW_UNPRODUCIBLE_FEATURES=all ...`,
    exit code 1 -- refused before any row was scored, printed as a message
    (not a traceback), same as U7's drift refusal.
  - `STOPTIMES_ALLOW_UNPRODUCIBLE_FEATURES=f4-unproducible` then served
    the same artifact successfully, logging the override loudly.
