# P1-C3 notes (artifact migration)

## `params` extraction is "everything not in a fixed metadata-key set", not a hyperparam allowlist

`_build_metadata` in `packages/models/src/stoptimes/models/compat/migrate.py`
computes `params` as every top-level key in the legacy `{key}_meta.json`
**except** a fixed, closed set of bookkeeping/derived keys already extracted
elsewhere (`model_type, dataset, route_id, features, n_samples,
train_samples, test_samples, val_samples, n_trips, metrics, model_key,
saved_at, model_path, provenance`).

I checked this against all 65 real `_meta.json` files in
`gtfs-eta/models/trained/` (read-only; nothing there was modified). The
top-level key union across every family (historical_mean, polyreg_distance,
polyreg_time, ewma, xgboost, lstm) is larger than the actual hyperparameters
per family -- it also includes derived/output fields the trainer happened to
put at the top level instead of nesting under `metrics`, e.g.
`unique_groups`, `global_mean_eta`, `test_coverage`, `n_features`,
`best_epoch`, `best_val_mae_seconds`, `epochs_trained`,
`train_wall_clock_seconds`, `n_groups`, `n_models`, `*_sequences`,
`target_stats`, `target_transform`, `seed`. With the closed-exclude-set
approach these all land in `params` alongside real hyperparameters
(`max_depth`, `degree`, `alpha`, `group_by`, `handle_nan`, ...).

This matches the task description literally ("known top-level hyperparam
keys not in a fixed metadata-key set") and is safe -- `params` is
`dict[str, Any]` on the contract and the full original dict is *also* kept
verbatim in `legacy`, so nothing is lost or misrepresented, it's just that
`params` is not a *pure* hyperparameter dict for these older artifacts. If
C1/T3 wants a stricter hyperparam-only `params` later, the per-family
allowlist would need enumerating (I did not do that here since it's not
narrow to migration and would need product input on which fields count).

## No real artifact had a `provenance` block

None of the 65 real legacy `_meta.json` files (all from the 2026-08-18 /
2026-08-24 / 2026-09-03 training runs) has a `provenance` key -- that field
was added to `ModelRegistry.save_model` (`build_provenance`) after these
artifacts were trained. So for every real artifact, `migrate()`:
- falls back `provenance.created_at` to `saved_at` (present on all 65), and
- leaves `provenance.lib_versions` as `{}` with a warning
  (`"no lib_versions in legacy provenance -- left empty, not invented"`),
  per the task instruction not to invent versions.

Manual check (6 real artifacts copied read-only from
`gtfs-eta/models/trained/` into a scratch dir under Claude's scratchpad,
never committed, deleted after the check):
`historical_mean`, `polyreg_distance`, `polyreg_time`, `ewma`, `xgboost` (all
`_mbta_bus_222_15_37_1d_*` variants) migrated cleanly; re-pickled
`model.pkl` loads with plain `pickle.load` (no `LegacyModuleUnpickler`
needed) and predicts identically (`np.allclose`) to the
`LegacyModuleUnpickler`-loaded original on a small synthetic frame built
from each model's declared `features`/`group_by` columns. The `lstm`
artifact was reported **skipped** with reason `could not unpickle model:
ModuleNotFoundError("No module named 'torch'")` -- torch isn't installed in
this worktree's `.venv` (matches Phase 0's parity note: "6 real
pre-migration artifacts load ... [lstm needs torch, not installed]").

## `polyreg_distance`'s legacy meta has no `features` key

The `_meta.json` for `polyreg_distance` (all variants checked) has no
top-level `features` list at all (only `polyreg_time`, `xgboost` do). This
isn't a migration bug -- `ArtifactMetadata.features` legitimately defaults
to `[]` when the legacy meta doesn't have one, same as any other missing
optional field. Flagging in case C1/T3 wants model cards to fall back to
introspecting the fitted model's `feature_cols` attribute for such
artifacts; out of scope here (migration only touches metadata + a faithful
re-pickle, never inspects a family's internals).

## Artifact-id sanitization: no real key currently needs it

All 65 real `model_key` values already match the contract's `artifact_id`
pattern (`^[A-Za-z0-9][A-Za-z0-9._=-]*$`) as-is -- `ModelKey.generate`'s
`_` / `-` / `=` character set happens to be a subset. `_sanitize_artifact_id`
exists for the general case (a `model_key` isn't guaranteed by the schema to
be filesystem/artifact-id-safe) and is covered by a synthetic test
(`test_artifact_id_is_sanitized_and_mapping_recorded`), but has no real
observed input to sanitize today.
