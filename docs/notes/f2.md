# F2 — native-artifact bridge for `stoptimes:<artifact>` (val)

## Defect

`packages/val/src/stoptimes/val/predictors/artifact.py`'s
`StoptimesArtifactPredictor.predict()` raised `RuntimeError` for any
registry artifact without `legacy` migration metadata -- i.e. every artifact
`stoptimes train run` produces. The quickstart's closing suggestion
(`--predictor stoptimes:quickstart-historical-mean`) failed for exactly this
reason. The module docstring claimed `core.features.registry` (T3) was
"still a placeholder" -- false: reading
`packages/core/src/stoptimes/core/features/registry.py` shows a complete,
tested `list_features()`/`get()`/`build()` API (temporal, spatial, segment,
rolling feature groups) that landed in Phase 2.

## Fix

`predict()` now branches on `artifact.legacy`:
- present (`stoptimes models migrate` output) -- unchanged: delegates to
  `GtfsEtaModelPredictor`/`estimate_stop_times`.
- absent (native, `stoptimes train run` output) -- loads the model with
  `stoptimes.serve.model_loading.load_artifact_model` (cached per
  `artifact_id` on the predictor instance) and scores it through
  `stoptimes.serve.pipeline`'s own `default_features`/`default_predict` --
  the same seam `stoptimes serve` uses for every native artifact. No new
  feature-computation code was written.

`MatchedObservation`s are built directly from val's already-matched
`trip`/`upcoming_stops`/`vehicle_state` (`_build_matched_observations`):
`distance_to_stop` from the difference of `Stop.progress_m` and
`VehicleState.progress_m` (both already assigned by
`val/engine/runtime.py` via `core.spatial.polyline`, the identical
projection `serve.pipeline.default_match`'s `_match_vehicle_position` uses),
and 0-indexed `stops_ahead`. `default_match` itself is not called --
val already did the equivalent matching before calling `predict()`.

One genuine gap noted, not worked around: `default_features` only carries
whatever a `match` stage attached to `.extra` (here: `distance_to_stop`,
`stops_ahead`) plus temporal features -- it has no notion of
`current_speed_kmh`/`bearing_to_stop`/shape-progress the way
`serve.estimator`'s legacy path does. A native artifact trained on those
richer features (anything beyond what `core.spatial.polyline`'s
`Stop`/`VehicleState.progress_m` and `core.features.temporal` can supply)
will still fail at serve time too, since this is a `serve.pipeline`
limitation, not something specific to val. Not something to route around
locally here -- it would need a `serve.pipeline.default_match`/`default_features`
change (out of scope, not owned by this track).

`default_features` also needs `ctx.source.timezone`/`.holiday_region` to
localize temporal features; val's `Predictor.predict()` only gets a bare
`source_id` string, not a real `Source`. Added a small local
`_ConfigLocale` shim in `artifact.py` (not a core/serve change) that reads
`core.config.get_config().default_timezone`/`.default_region` -- the same
config values `estimate_stop_times` (the legacy path) already uses, so both
paths localize the same way instead of the native path silently defaulting
to UTC/no-holiday-region.

## Verification

- `packages/val` suite: 475 passed, 1 skipped (pre-existing, unrelated).
- `test_native_artifact_predictor_agrees_with_serve_pipeline` (new): trains
  a real `historical_mean` artifact via `stoptimes train run`, then scores
  the same vehicle position two ways -- `StoptimesArtifactPredictor.predict()`
  and an independent from-scratch `stoptimes serve` pipeline run
  (`build_default_pipeline()` with real `default_match` map-matching against
  the same `mini_gtfs.zip`) -- and asserts the horizons agree exactly.
- `test_quickstart_closing_suggestion_via_val_replay_cli` (new): CLI-level,
  `typer.testing.CliRunner` against `stoptimes val replay --predictor
  stoptimes:<artifact>` with `STOPTIMES_MODEL_REGISTRY_DIR` (no `--registry`
  flag on `replay`), asserts real scored rows come out.
- Manually ran the quickstart's closing command end to end (own scratch
  registry + a real trained artifact + `mini_gtfs.zip`, not the read-only
  `/tmp/stoptimes-usertest` tester fixture): `stoptimes val replay --source
  mbta --predictor stoptimes:quickstart-historical-mean ...` → `Samples=9
  Arrivals=6 Results=6`, non-empty `predicted_arrival_epoch` column. No
  errors, no silent drops.
