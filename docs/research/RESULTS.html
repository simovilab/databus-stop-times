roadmap 3.2 · shuffle-label control

Permute the target within train + val (features untouched, test untouched) and retrain. A model can then only learn noise, so its metrics must collapse to the naive constant-predictor reference. Hyperparameter tuning (Optuna)

120 trials/agency · 9 params + early stopping · tuned on val, tested once

Roadmap 5.1: the validation split was computed but never used, and every hyperparameter was hardcoded. A TPE study scored on the validation split of each segment corpus, selecting the best config by val MAE — the test set is touched only once, for the chosen config. The search covers nine XGBoost hyperparameters: the five structural ones plus the four regularization knobs (min_child_weight, reg_alpha, reg_lambda, gamma) now wired through train_xgboost. A final pass added early stopping on the validation split — the tree count grows until val MAE stops improving (patience 50, cap 3000) instead of a tuned n_estimators. Adding regularization and early stopping sharply helped the data-poor agency; the data-rich one plateaued.

Feature probe · scheduled segment duration does not break the MBTA plateau

If MBTA is feature-limited, the obvious first feature is the scheduled segment duration (sched_arrival(to) − sched_arrival(from) from the GTFS snapshot) — a serveable, leakage-free prior. Trained on the identical row set and split (tuned config + early stopping; uncovered rows keep NaN, routed natively), it moved nothing: test MAE 23.90→23.88 s (+0.1%), R² 0.659→0.661 (+0.002), and sched_dur did not reach the top-5 importances (dominated by progress_ratio 0.58, is_at_stop 0.14).

Why: the target is time remaining from the current position to the next stop, not full-segment traversal, so it is dominated by how far along the vehicle already is (geometry). A full-segment scheduled duration is both redundant with that geometry and mismatched to a partial-remaining target. Since GTFS schedules are built from historical running times, this also lowers expectations for empirical segment identity (target encoding) — between-segment differences are already captured. The residual is within-segment live variance (moment-to-moment congestion), which no static, serveable feature can see. Moving MBTA further needs a live rolling-conditions signal (a serving-side feature store), not another static feature.

07

LSTM over segment sequences — a split decision

roadmap 5.2 · causal GRU/LSTM · tuned on val, tested once

The segment reformulation was chosen partly because it gives a natural sequence for a recurrent model to consume: one trip instance, keyed (trip_id, service_day) and ordered by segment_index, so the prediction at each stop can see the trip's own upstream history. The model is unidirectional by construction — the prediction at segment t may depend only on segments 0..t — which is what keeps the offline metric something serving could actually reproduce; a perturb-at-t test enforces it. Splits, rows and metric keys are identical to the XGBoost study, so the two families are directly comparable.

The first result was a bug in the loss, not in the architecture

Untuned smoke runs looked hopeless — MBTA 35.5 s / R² 0.035, bUCR 75.4 s / R² −0.431 (worse than predicting the mean). Neither was an architecture failure. The target is right-skewed seconds and the loss was unstandardized, so large errors were under-weighted, and both runs were still improving at the 30-epoch cap. Adding a target_transform and letting the run converge (300 epochs, patience 25) reached MBTA 25.5 s / R² 0.601 and bUCR 26.9 s / R² 0.801 before any hyperparameter search at all. standardize beat log1p beat none on both agencies.

This also settles an open question: bUCR's negative R² was under-training, not insufficient data. The worry that ~5.7-segment sequences over 11k rows are too short and too few for a recurrent model to learn from turned out to be wrong — they were sufficient once the target was scaled.

Formal splits — and the purge trap that would have wrecked MBTA

roadmap 3.2 · models/common/splits.py · 21 tests

A shared day_grouped_split/fraction_split now backs every split in the repo (calendar-boundary cut, optional group purge, optional embargo, a content-hash tiebreaker so shuffled input reproduces byte-identical splits). It reproduces every published split exactly — no number above moves. The reason it took a dedicated module: the obvious “fix” (purge on trip_id) is wrong for MBTA and would have silently thrown away almost the entire validation set.

The unit of leakage is the trip instance, not the trip id

MBTA reuses one trip_id across every weekday it runs (1,130 distinct ids across 153,498 rows / 16 service days — the same fact that drove the service-date fix in §05). Purging on trip_id alone therefore treats nearly the whole corpus as one giant group: the val split collapses from 32,534 rows to 189. The leakage unit that actually matters is (trip_id, service_day) — one concrete trip running on one concrete day. temporal_split defaults to purge=False and instead takes a service_offset_h to compute service-day boundaries correctly; with it, MBTA purges 314 rows of genuine cross-boundary leakage rather than ~88,000 rows of nothing. A purge removing more than 5% of a split now raises a RuntimeWarning so this doesn't silently recur elsewhere.

09

Statistics layer — CIs, paired tests, correction

roadmap 4.3 · models/evaluation/stats.py · 37 tests

Bootstrap CIs (i.i.d. and cluster/group), paired significance tests (Wilcoxon, Diebold–Mariano with Newey–West HAC variance, cluster-aware paired bootstrap), and Holm / Benjamini–Hochberg multiple-comparison correction, plus a compare_all() that emits the paper's comparison table directly. This is the machinery every result from §10 onward is scored through, and it is what powers the live-validation table in §14.

The cluster bootstrap is the correct estimator here, but its effect is smaller than assumed. On the real MBTA test split, cluster-bootstrap CIs (grouped by trip) do not systematically widen versus i.i.d. bootstrap CIs — the ratio of CI widths ranges 0.74–1.02 across the metrics checked, even though the same estimator widens CIs by >1.5× on a synthetic case built with strong within-cluster correlation. Use the cluster estimator as the default (it is never wrong to use it), but don't assume it will visibly change a conclusion — on this dataset it mostly doesn't, and that should be reported rather than assumed away.

Live rolling-conditions features — nudging the MBTA plateau

feature_engineering/rolling_conditions.py · 7 features, 4 families · 10 tests

§06's feature probe showed a static feature (scheduled duration) can't move MBTA's plateau; this asks whether a live one can. Seven features across four families — recent segment traversal EWMA + ratio, headway/leader-bunching, route congestion index, vehicle recent delay — computed as one chronological pass with a genuine point-in-time merge_asof join (a traversal enters state only once completed; baselines are causal expanding means, never a whole-corpus mean). The headline test perturbs every observation after time t and asserts the features computed at t are byte-identical.

Discipline point: polyreg_time's apparent 4.7× short-horizon advantage over the agency feed is not statistically significant (p=0.44) — exactly the overclaim the §09 statistics layer exists to prevent. Report the CI, not the point estimate.

Root cause — established by evidence, two hypotheses tested, one falsified

Hypothesis 1, falsified: “the models were trained on a 5-stops-ahead window, so they never saw long horizons.” The stop-level training set (2,030,210 rows) has 14.4% of rows above 10 minutes, p99 = 48 min, max = 116 min. Offline, on held-out rows, the models track long horizons fine (true 1884 s → xgboost predicts 1730 s in the 20–50 min bucket). The models are not the problem.

Hypothesis 2, confirmed: “the serving path computes different features than training did.” Two concrete defects: (a) stops_ahead was served as idx+1 while the dataset builder labels the closest upcoming stop 0 — a one-off, fixed this session. (b) far more consequential: when no route shape is supplied, the estimator falls back to straight-line haversine distance, hardcodes cross_track_error=0.0, and leaves is_at_stop False where training saw it True 67% of the time. Measured shape÷haversine distance ratio by horizon: 1.00 at <2 min, 1.10 at 2–5 min, 1.24 at 5–10 min, 0.28–0.34 at 20–50 min (where the route loops back). The fallback is harmless at short horizon and diverges badly exactly where the collapse happens; distance is the dominant feature (§06, §11), so a wrong distance yields a wrong time in one direction — which is why bias ≈ −MAE.

FIXED (a) only — eta_service/estimator.py, with a regression test, plus a fix to a pre-existing test-isolation bug where test_shape_hook.py reset only one of the two registry singletons. A 30-minute post-fix run shows a short-horizon sign flip — xgboost goes from +42.9% worse than the agency feed to −38.4% better (p=1.5e-18) — but that headline overstates the fix, and the decomposition matters more than the flip. Of the two terms in the ratio, ours moved a little and the baseline moved a lot: xgboost MAE improved 65.7 → 58.2 s (−11%), while gtfsrt in the second window degraded 40.5 → 88.0 s (+117%). The agency feed's short-horizon MAE is also extremely noisy — 95% CI [15.2, 71.3] before and [34.6, 160.4] after, heavily overlapping — so most of the swing is baseline variance, not model improvement. The honest claim for the stops_ahead fix is ~11% short-horizon MAE, not a sign flip. >10 min remains ~4–5× worse as expected. Caveat: the two runs are unpaired 30–45 minute windows at different times of day (17:00–20:45 vs 20:51–21:24 EDT) on different route mixes — directional only, not a controlled A/B.

OPEN (b) is not fixed and is the important remaining item. The shape hook already exists in estimator.py and databus populates it in production; nothing populates it for any other caller. Production may well be fine while every standalone caller is silently degraded — that needs confirming separately. This is squarely roadmap 1.2 and overlaps 1.7.

Which artifact this measures. The registered/served MBTA xgboost artifact records test_mae_seconds = 109.99 in its own metadata — it is a stop-level model from 2026-08-18, not the 24.6 s tuned segment model of §06. The live numbers above measure the stale artifact, not the segment-corpus leaderboard elsewhere in this ledger. Stated explicitly so no one reconciles 71 s against 24.6 s again.

Provenance & caveats

  • Numbers are rehearsal-corpus results measuring pipeline correctness and experimental design — not the transferable 90-day replication numbers (window 2026-08-14 → 2026-11-12).
  • bUCR and MBTA corpora differ in fix cadence (~80 s vs 5 s), so segment-level results are not directly comparable across agencies.
  • bUCR segment target is position-derived (50 m first-within, else closest-approach ≤200 m); holdout is day-grouped so whole trips stay within one split.
  • MBTA segment corpus is 153,498 segments / 16 days (all service-days; trip instances split by service date — see §05); the schedule baseline covers 70% of test segments.
  • Every saved model now stamps git SHA, library versions, dataset SHA-256, and seed (models/common/provenance.py); fixed-seed reruns reproduce metrics.
  • HPO (§06) tunes on the validation split only; the test set is evaluated once for the val-selected config. Seed 42, 120 TPE trials/agency over 9 params (structural + min_child_weight/reg_alpha/reg_lambda/gamma) plus early stopping on val (patience 50, cap 3000; the tree count is chosen, not tuned) — all wired through train_xgboost, all trials recorded to scratchpad/hpo_trials_*.csv. bUCR improved at every step (10.8→14.9→16.4%); MBTA plateaued near 24.6 s / R² 0.65, indicating its remaining error is feature-limited, not tuning-limited. Tuned configs are not yet promoted to the served registry.
  • §08–§13 splits and metrics all run through the shared models/common/splits.py (day-grouped, purge=False by default, embargo via service_offset_h) and models/evaluation/stats.py (i.i.d. and cluster bootstrap, Wilcoxon / Diebold–Mariano, Holm / BH correction) — the same machinery, not a one-off script, so numbers across sections are comparable.
  • §14's live-validation run is not reproducible from this repo alone: it depends on the sibling etaval repo, a live 30–45 minute window against the real MBTA GTFS-RT feed, and whatever traffic happened to exist during that window. Treat it as a point-in-time measurement of the currently registered artifacts, not a number that will replay identically on a re-run — the pre-fix/post-fix comparison in §14 is explicitly caveated as directional for exactly this reason.
